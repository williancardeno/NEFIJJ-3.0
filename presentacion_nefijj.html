Presentación del proyecto · 5–7 minutos

NEFIJJ 3.0

Gestión y seguimiento de incidencias para instituciones con varias sedes.

Aplicación móvilAPI RESTAcceso por rol y sede

Guion de exposición basado en el estado documentado del proyecto.

01 · La necesidad

Los reportes se dispersan.
El seguimiento se dificulta.

1

Canales separados

Los reportes pueden llegar por conversaciones, llamadas o mensajes distintos.

2

Poca trazabilidad

Cuesta reunir evidencia, identificar responsables y conocer el avance de cada caso.

3

Varias sedes

La institución necesita organizar la atención y limitar el acceso al ámbito correcto.

La problemática es el objetivo del proyecto; no se presenta como resultado de un estudio de campo documentado.

02 · La solución

Un ciclo común para reportar y atender.

01 · VincularCuenta existente + invitación QR de un solo uso›
02 · ReportarCategoría, prioridad, descripción y foto opcional›
03 · AsignarRuta de técnico por categoría y sede›
04 · AtenderPendiente → En proceso → Resuelto›
05 · ConsultarHistorial dentro de los permisos de cada rol

La asignación automática requiere que el administrador haya configurado una ruta para la categoría y sede.

03 · Usuarios y permisos

Cada rol ve lo que necesita para actuar.

Estudiante / usuario

Se vincula a una sede, registra incidencias y consulta sus propios reportes.

Técnico

Consulta incidencias de su sede y actualiza solo las asignadas a su cuenta.

Administrador

Gestiona sedes, técnicos, categorías, rutas e invitaciones de su organización.

Superadministrador

Administra organizaciones y consulta incidencias globales en modo de lectura.

La API valida rol, membresía activa y estado de organización y sede.

04 · Cómo funciona

Una app móvil conectada a una API protegida.

React Native + Expo · Django REST Framework + JWT · MySQL local · evidencia en archivos servidos con autorización

05 · Demostración sugerida

Recorrido de la aplicación.

1

Acceso y vinculación

Iniciar sesión con una cuenta provisionada y aceptar el QR de una sede.

2

Nuevo reporte

Crear una incidencia, seleccionar categoría y prioridad, adjuntar foto opcional.

3

Atención técnica

Consultar el caso desde la cuenta técnica y avanzar el estado si está asignado.

4

Administración

Mostrar categorías y asignación por sede; cerrar con supervisión de organizaciones.

Si MySQL o las migraciones no están validadas, explica el flujo o usa capturas marcadas como ilustrativas. No simules una operación real.

06 · Autorización por rol

La API verifica el contexto antes de actuar.

La organización y el ámbito solicitado deben estar activos. El acceso se limita por rol y membresía.

07 · Modelo de datos vigente

La incidencia conecta organización, sede, categoría y personas.

El diagrama resume los modelos Django actuales. Invitaciones y rutas requieren revisar sus migraciones antes de usarlas en MySQL.

08 · Estado actual y límites

Hay una base funcional; quedan validaciones importantes.

El repositorio contiene código para autenticación, incidencias, evidencias, invitaciones y administración.
La documentación registra pruebas de backend en SQLite temporal.
La prueba integral en teléfono físico con Expo Go sigue pendiente.
Las migraciones nuevas requieren revisión antes de aplicarse a la base MySQL existente.
Protocolos operativos, alertas y recuperación de contraseña no están implementados.
No hay evidencia documentada de despliegue productivo ni medición de impacto.
No presentar las funciones presentes en el código como validadas en producción.

09 · Cierre

Más trazabilidad para la atención diaria.

NEFIJJ busca centralizar el reporte y seguimiento de incidencias, manteniendo el acceso limitado al ámbito de cada usuario.

La API valida membresías, rol y estado de organización y sede.

No. Vincula una cuenta existente que ya inició sesión.
